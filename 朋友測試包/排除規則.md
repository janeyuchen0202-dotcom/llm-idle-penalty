# 朋友電腦閒置測試：排除規則（2026-10-15 定案，10/16 補「睡著或卡住」「螢幕狀態」，並依外部審閱補「確認不了」的處理；10/18 補「用錯顯示卡」）

> 這份規則在發給朋友、看到任何結果之前就定好，所有機器都用同一套。
> 把這個檔案用 LINE 或 email 傳給自己，留下時間證明（要在收到任何朋友的結果之前）。

## 1. 整輪不算（程式每輪結束時自動檢查，分析時用同樣的紀錄再算一次）

- GPU 測試時，模型沒有完全放進顯示卡（10/16 改成下面的判斷方式，原因：這版 llama.cpp 平常的紀錄不寫放了幾層）
  - 開始前先用詳細紀錄啟動一次伺服器，看「offloaded X/Y layers」。X 不等於 Y，代表這張卡放不下，每一輪都不算
  - 每一輪再量伺服器占用的顯示卡記憶體。比開始前少 5% 以上，代表這次放得比較少，那一輪不算
  - 10/16 在 RTX 4050 量到的參考值：全部放進去 2.05 GB，故意只放 10 層 0.81 GB
  - 確認不了（讀不到層數、也讀不到記憶體）的輪次記成「未知」。分析時用服務時間檢查：那一輪一個接一個的服務時間，比同一台其他輪的中位數慢 30% 以上，就當成放得比較少而排除；否則照算，並列出有幾輪是未知
- GPU 測試：這一輪的伺服器用的不是要測的那張顯示卡（10/18 加，第 3 台發現的）
  - 測試包開始時照順序選顯示卡（例如 Vulkan0），之後每一輪都用同一個編號。有內顯的電腦，順序可能中途改變，伺服器就跑到內顯上
  - 分析時讀每一輪伺服器紀錄的顯示卡清單：用的那個編號對到的名稱，和要測的顯示卡不同，那一輪就不算
  - 這條是看到怪數字（一個接一個慢 3.8 倍）之後查到原因才加的，照第 7 點處理：有紀錄才排除（伺服器紀錄的清單，加上 nvidia-smi 顯示要測的卡在請求進行中完全閒著）。加了之後所有機器都重新檢查過
- 有請求失敗（沒有輸出任何 token，或連線錯誤），或伺服器中途當掉、這一輪沒跑完
- 這一輪中，筆電有任何時候在用電池
- 等待期間 CPU 太忙：閒置 2 秒以上的那幾段等待，CPU 平均使用率超過 30%
  - 程式在每段等待的前後讀 Windows 的系統 CPU 時間來算，記在 requests.csv 的 cpu_wait 欄
- GPU 測試：等待期間顯示卡被別的程式使用，平均使用率超過 10%
  - 等待時測試自己沒在用顯示卡，量到的使用率都來自別的程式（例如影片、遊戲、動態桌布）。這時顯示卡沒有真的閒下來，量不到閒置效應
  - 每段等待去掉開頭 1.2 秒和最後 0.2 秒，因為使用率是往前平均的，開頭會混到上一個請求
  - NVIDIA 用 nvidia-smi 的紀錄，其他顯示卡用 Windows 的 GPU 3D 使用率
  - 不記錄狀態的對照輪（第 5、10 輪，和補它們的輪次）沒有這項紀錄，這條不適用
  - 有記錄、但等待期間的紀錄少於 20 筆的輪次，記成「無法判定」：照算，但分析時另外列出，並報告排除它們之後結果有沒有變
  - 非 NVIDIA 的數字是各程式 3D 引擎使用率的加總，可能超過 100%，和 NVIDIA 的整體使用率不是同一種數字；門檻都用 10%
- 電腦中途睡著或卡住（10/16 加）：某段等待或某個請求，比應該的時間多出 2 秒以上，或一個請求超過 120 秒
  - 例如筆電闔上睡著、Windows 的連線待命。程式同時比對牆上時間和程式計時，記在 requests.csv 的 stall 欄
  - 正常的情況下多出的時間不到 0.01 秒，所以 2 秒不會誤判

## 螢幕狀態（10/16 加）

螢幕開著或關掉都算數，包括桌機關掉螢幕電源、筆電闔上但設定成不睡。程式每輪開始和結束時記錄作用中的螢幕數；NVIDIA 顯示卡另外記錄 Display Active。同一台如果兩種狀態都有，分析時分開比較，有差異就照實寫。

## 2. 其他意外

停電、當機、有人中途用電腦、系統更新這類問題，程式偵測不到，但有紀錄或朋友說明可以證明的，那一輪也不算。

## 3. 只刪單一請求

比同一輪、同樣閒置秒數的請求中位數慢 3 倍以上的，只刪那一個請求。

## 4. 補跑

- 有幾輪不算，程式就自動在最後多跑幾輪補上，最多補原定輪數的一半：5 輪最多補 3 輪，10 輪最多補 5 輪。補跑的輪次照樣檢查
- 模型放不進顯示卡的情況：開始前確認這張卡放不下，就不補跑，因為顯示卡記憶體不夠，補跑也一樣。放得下、只是某一輪放得比較少，就補跑
- 第 2 點的意外要等結果回來才知道：排除之後有效輪數不到原定輪數，就請朋友在收件期限內再跑一次補上
- 補跑和重跑的結果全部採用，不挑

## 5. 補完還是不夠

有幾輪用幾輪，論文照實寫。有效的少於 3 輪，整台不採用。

## 6. 照實報告

- 每一筆排除都列出來：哪一台、哪一輪或哪個請求、原因
- 排除與否會讓結論不同的話，兩種結果都報

## 7. 規則沒寫到的問題

事後才發現的問題，理由必須是「實驗過程出了事，而且有紀錄」，不能只因為數字看起來怪。看到怪數字先查原因，查到有紀錄的原因才排除，並照第 6 點報告。

例子：修正紀錄 #9。9/20 那組看起來像系統塞爆了，10/5 才查出是筆電中途睡著。請求的送出時間有斷層，也和 Windows 的睡眠紀錄對得上，所以那組作廢。
