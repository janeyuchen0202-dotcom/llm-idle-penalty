## 測試內容（和論文相同的部分）

- 同一版 llama.cpp（b9549）、同一個模型檔（SHA-256 核對）、同樣的請求格式（temperature 0、ignore_eos、每個請求前面加不重複的編號）、`--cache-ram 0`、`-c 4096`、`--parallel 1`
- 閒置時間 0、2、3、5、8 秒，順序隨機；每輪 4 個區塊 × 5 種 × 3 次 = 60 個請求，和 10/11 鎖時脈那組相同
- GPU 測試：838 token prompt、128 token 輸出（和 RTX 4050 的 0.29 秒比）；太慢的機器（暖機時一個請求超過 8 秒）自動改用 118／16
- CPU 測試：118 token prompt、16 token 輸出（和論文 HP 純 CPU 比）；用 CPU 版 llama.cpp，確定完全不用 GPU；執行緒數＝實體核心數

## 和論文不同、要記得的地方

- **每輪重新啟動伺服器**（現在跑 5 輪、睡前跑 10 輪）：可以看同一台機器每次啟動之間的差異
- **第 5、10 輪不記錄 GPU／CPU 狀態**：當對照，確認記錄程式本身不影響結果（論文 RTX 4050 也做過 nolog 的檢查）
- **睡前跑的第二個測試（CPU）不會停下來問問題**：開跑前太忙、沒插電都只記錄，不暫停（朋友已經睡了）
- **選顯示卡用名稱判斷，不用記憶體大小**：內顯會回報借用的系統記憶體（例如使用者的筆電 32 GB → Iris Xe 報 16 GB），比獨立顯示卡還大。NVIDIA 一律算獨立；AMD 名稱有 RX 或 Pro 才算獨立；Intel 只有 Arc A／B 系列算獨立。沒有獨立顯示卡就用內顯，結果標「內顯」
- **GPU 測試用 `--device VulkanN -ngl all`**：強制整個模型放進選定的顯示卡；伺服器紀錄裡的「offloaded X/Y layers」會一起存下來
- **AMD 沒有時脈紀錄**：Windows 拿不到 AMD 的時脈，只能記錄使用率；原因（是不是降頻）要靠和同一台的 CPU 測試對照
- 每台跑一次（5 輪），不同機器之間的差別很多（世代、驅動、電源設定、背景程式），論文只能寫「在我們測的機器上」

## 自動收集的資訊（10/14 使用者：能加的都加，之後再決定要不要用）

- 只讀取、不改任何設定、不需要系統管理員；不收序號、程式清單、網路資訊
- `hardware.json`：CPU（型號、核心、快取）、電腦型號、機殼類型、記憶體條（容量、速度）、每張 GPU（型號、驅動版本和日期、解析度、更新率）、啟用中的螢幕數、Windows 版本和代號、開機時間、硬體加速 GPU 排程、Windows 電源模式（效能／平衡／省電的 overlay GUID）、電池
- `hardware.json` → `power`：目前的電源計畫，以及 CPU 最低／最高效能狀態、CPU 加速模式、PCIe 連結省電的插電與電池設定（powercfg 只查詢；中文輸出用系統字碼頁讀）
- NVIDIA：開始、每輪結束、全部結束各存一次 `nvidia-smi -q`（含降頻原因、功耗上限、P-state）；每 100 ms 的紀錄欄位刻意不擴充，免得舊驅動不認得某個欄位而整個失敗
- `run_info.json`：llama.cpp 版本、Python 版本、選到的裝置、執行緒數、工作負載、每輪的暖機時間和模型放置
- 讀不到的：筆電品牌的效能模式（Armoury Crate 等）和 MUX 獨顯直連 → 請借筆電的朋友自己回報

## 排除規則和補跑（10/15）

- 規則全文在 [排除規則.md](排除規則.md)。使用者決定：有幾輪不算就補跑幾輪（取代原本的「剩不到一半就整台不用」）；其他照 Claude 的草案
- 每輪結束時程式自動檢查：模型沒全放進顯示卡、請求失敗或伺服器中斷、用電池、等待時 CPU 平均超過 30%、GPU 測試等待時顯示卡平均超過 10%
- 不算的輪次：在最後補一輪，記不記錄狀態和被補的那輪一樣；最多補原定輪數的一半（5→3、10→5）。模型放不進顯示卡、而且之前沒有一輪放得進去，就不補（顯示卡記憶體不夠）
- 新的紀錄：
  - requests.csv 多了 `cpu_wait`（這段等待的 CPU 使用率 %，只有閒置 2 秒以上才算）和 `error`
  - run_info.json 的每一輪多了 `valid`、`invalid_reasons`、`cpu_wait_percent`、`gpu_wait_percent`、`gpu_wait_samples`、`makeup`
  - 整體多了 `rounds_planned`、`makeup_cap`、`makeup_rounds`、`valid_rounds`
- 程式的檢查只決定要不要補跑；分析時用同樣的紀錄重新判斷，原始資料全部保留，不會因為判斷不算就刪掉
- 測試：`--quick --force-invalid` 把第 1 輪當成不算，用來在使用者的電腦上確認補跑會動
- 改之前的版本備份在 `備份/`

### 資料欄位的意思（審閱建議寫清楚）

- `out_tokens`：收到文字的串流片段數。llama-server 通常一個片段一個 token，但不保證；只用來判斷請求有沒有輸出（0 就是失敗）
- `gpu3d_sum`（非 NVIDIA）：各程式 3D 引擎使用率的加總，可能超過 100%，和 NVIDIA 的 `utilization.gpu` 不是同一種數字
- CPU 測試和 GPU 測試用的工作負載不同（118/16 和 838/128 token；太慢的 GPU 也會改用短的），所以只比較同一個測試裡「閒置後」和「一個接一個」的差別，不拿 CPU 和 GPU 的延遲互相比

## 朋友電腦上的保護措施

- 執行期間防止睡眠和關螢幕（程式結束自動恢復）；關掉主控台的快速編輯（不然點一下視窗就會卡住）
- 筆電沒插電就先等插電；開跑前 CPU 超過 30% 或 GPU 超過 15% 就提醒先關程式
- 每個請求的結果即時寫入；中途關掉或出錯也會把跑完的部分打包（檔名加「未完成」）；被重開機打斷的話，下次執行任何一個測試時會先把沒打包的結果補包到桌面
- 睡前跑的關機：`shutdown /s /t 120`（Windows 會強制關閉其他程式，所以開始前提醒存檔），倒數時按任意鍵執行 `shutdown /a` 取消
- 結果 zip 直接存到桌面（被 OneDrive 接管也找得到），使用者名稱、電腦名稱、路徑都遮掉
- 清理：只刪 MANIFEST.txt 上列的檔案和 `_kit\work`；先核對識別檔，C_清理被拖到別處就拒絕執行；刪之前問 Y/N；桌面的結果 zip 不在資料夾裡，不會被刪；資料夾裡如果有別的檔案也不動
- BAT 內容只用英文字元（cmd 讀中文會亂碼）；中文訊息都由 Python 和 PowerShell 顯示
