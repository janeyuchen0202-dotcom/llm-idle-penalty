## 事後檢查（看過結果才做，不算預測；check_queue_runs.py）

- 量測區間實際的負載 ρ̂：0.789（ρ = 0.7）、0.553（0.5）、0.389（0.3）
- 排隊中請求的服務時間：ρ = 0.7 是校正 b 的 1.020 倍，而且最後四分之一變慢（1.103、1.094、1.096、1.139 秒）；ρ = 0.5、0.3 是 0.997、0.990 倍
- 溫度和時脈（忙的時候）：ρ = 0.7 溫度中位數 80 度，最後四分之一 89 度、時脈 1770 → 1635 MHz；ρ = 0.5 是 68 度、1800 MHz；ρ = 0.3 是 62 度、1815 MHz。連續請求時一直 89 度、時脈 1605–1650 MHz（校正時 1830）。整段最高 91 度（03:56:55）；90 度以上的有 980 筆（03:28–03:57）
- **朋友說的「95 度」**（03:37 記在設計說明.md，結果還沒收到時）：記錄的是核心溫度，最高 91 度，所以 95 度應該是熱點溫度。這台確實過熱降頻：10/20 閒置測試時核心最高才 66 度，持續負載下到 89–91 度
- 用每組自己排隊請求的服務時間重新模擬（其他和方法 1 相同）：ρ = 0.7 2.373（實測 2.486，原本 2.160）、ρ = 0.5 0.403（0.414）、ρ = 0.3 0.433（0.429）→ ρ = 0.7 方法 1 少算的 0.326 秒，約三分之二是服務時間變長（1.020 倍，被 1/(1 − ρ) 放大）
